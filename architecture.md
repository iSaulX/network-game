## Purpose

Parchís Stars, a networked Parchís game built with Next.js and a hand-drawn UI. Work is split across multiple AI contributors: task briefs live in `tasks/`, and each contributor implements one task at a time.

## Stack

- **Framework:** Next.js 16.4.2 (App Router, Turbopack)
- **React:** 19.3.0
- **Language:** TypeScript
- **Styling:** Tailwind CSS v4 (`app/globals.css`) with **OpenRunde** loaded via `next/font/local` from `public/fonts/` (400/500/600/700) and applied app-wide
- **UI chrome:** `drawably/react` 0.4.2 — real HTML controls with seeded SVG sketch chrome
  - Used for all non-game UI: homepage, menus, lobby, forms, buttons, dialogs, settings, pre-game/post-game screens
  - **Exception:** the homepage avatar picker popover uses **HeroUI** by explicit user request. The popover trigger and avatar option buttons are still drawably controls.
  - `drawably/style.css` is imported exactly once, in `app/layout.tsx`
  - Theme through custom properties: `--drawably-stroke`, `--drawably-fill`, `--drawably-paper`, `--drawably-width`
  - Do not restyle drawably's SVG paths or fake the look with CSS borders
- **Text and motion:** `torph` 0.1.4 (`torph/react`'s `TextMorph`) animates in-place text changes; the free transitions.dev recipes (skeleton reveal, icon swap, success check) are vendored into `app/globals.css` as `.t-skel`, `.t-icon-swap` and `.t-success-check` with `prefers-reduced-motion` guards
- **Feedback:** `web-haptics` 0.0.6 (`useWebHaptics`) for optional Web Vibration API patterns, plus `components/game/game-feedback.ts`
  - The owner-supplied clips `/sounds/dice-roll.mp3` (dice taps/rolls) and `/sounds/click.mp3` (every actual chip movement: advance, bonus move, barrier break) are preloaded into `HTMLAudioElement`s
  - The remaining cues (selection, UI tap, start, capture, goal, barrier, warning, entry, win/loss, your-turn) are short synthesized Web Audio envelopes; automatic entries do not play the movement clip
  - `/play` exposes a header **Sonido** button and a drawably popover: a top **Silenciar todos los sonidos** checkbox plus per-category checkboxes (Interfaz, Dados, Movimiento, Entrada de ficha, Capturas, Barreras, Meta, Avisos, Victoria y derrota, Tu turno). Checked means silenced; changes apply live. The settings are browser-memory only.
  - Haptics are reserved for human actions or consequences that affect the human; bot actions and auto-play contribute sounds only; sound mutes do not disable haptics
  - Audio stays silent before the first pointer/keyboard gesture and opens lazily on it; unsupported haptics no-op, playback failures are caught, and the game works with no feedback
- **Game rendering:** **PixiJS** (`pixi.js` 8.22.0) — board, chips, board animations, legal-move highlights, and every board/game-state update
  - One Pixi `Application` mounted in a client component; React handles mounting plus the UI around it
  - Drawably controls cannot live inside the Pixi canvas
  - The `/play` board, chips, turn highlights and chip interpolation are PixiJS in `components/game/`; the reusable local/bot `GameStage` remains Task 06, but the board/dynamic-layer split is already in place
  - **Requested exception:** at the project owner's request the two-dice controls are DOM drawably cards placed above/below each player card, not Pixi sprites. They are the only game controls outside the canvas; all board/token rendering remains Pixi.
  - PixiJS is imported dynamically inside the client effect so the canvas never runs during server rendering
- **Offline:** generated, prefixed service worker (`scripts/service-worker-template.js` → `public/sw.js`) — versioned precache of the shell, every route, all `/_next/static` files and every public asset; network-first navigations with `/offline` fallback; production-only registration. See “Offline shell” below.
- **Desktop:** Tauri v2.12 (`tauri/src-tauri`) wrapping a fully static Next.js export (`TAURI_BUILD=1` → `out/`). Every route, script, stylesheet, font, image and sound is embedded in the native binary, so the desktop app works with no network and without a service worker. See “Desktop (Tauri)” below.
- **HeroUI (popover exception):** `@heroui/react` v3.2.6 `Popover.Root`/`Trigger`/`Content`/`Dialog` for the homepage avatar picker only
  - Styles come from `@heroui/styles` (utilities, variants, default theme, popover component CSS) plus `tw-animate-css`, imported in `app/globals.css`
  - The app's paper theme overrides the HeroUI overlay tokens (`--overlay`, `--overlay-shadow`)
  - Do not use HeroUI for other controls unless a task explicitly asks
- **Unused for now:** `@heroui/react` / `@heroui/styles` outside the avatar popover; do not use them elsewhere unless a task explicitly asks
- **Realtime (pending Task 04):** custom Node server (`server.ts`) + `ws`; Next route handlers for HTTP; in-memory `PartyStore` on `globalThis`
- **Package manager:** bun 1.4.2

## Unified setup flow (`/`, implemented)

- **Route:** `/` is `app/page.tsx`, a thin client-rendered entry that mounts `components/setup/setup-flow.tsx`. Everything the player does before the board is one component with a `Step` state machine: `home → create | join → lobby → game`. The header carries the brand icon, the highlighted **Parchís Stars** title and a drawably badge naming the current step; clicking the brand returns home and aborts any online session.
- **Home:** two columns. The profile card keeps the large drawably-circled avatar, the controlled **Tu nombre** input (`maxLength={24}`, selectable) and the shared HeroUI **Cambiar avatar** popover, and now persists to `localStorage` (`parchis.profile.v1`) when a game starts. The right column has two cards: **Crear una partida** (copy: you can play online against other people or against bots, and choose the mode, connection and start time) and **Unirse a una partida** (six-character code from the host). The old **Jugar 1 contra 1** and **Jugar solo con bots** cards are gone.
- **Random identity:** the prefilled name and avatar come from `useSyncExternalStore` with stable server snapshots (an empty name and index 0), so the prerender never observes `Math.random()` — which Next 16 rejects during static prerendering. The random/saved pick happens on hydration.
- **Create step:** the **¿Partida en línea?** card offers **Sí, con personas** and **No, contra bots**; the bots option also shows the four board colours (blue/red/yellow/green) for the human. The **Modo de juego** card shows the supplied `modes/1vs1.png` and `modes/all-for-all.png` art for **1 contra 1** and **4 jugadores · todos contra todos**. Choosing a mode with bots navigates to `/play?mode=&color=&name=&avatar=`; choosing it online creates a room and moves to the lobby.
- **Join step:** a code form (6 chars, uppercased) that opens the guest lobby. Failures come from `LOBBY_FAILURE_COPY` in Spanish. When WebRTC is unavailable the card explains it with `LAN_SUPPORT_COPY` instead of showing the form.
- **Connecting state:** while the host is creating the room, a guest is joining, or a guest has not received its first roster, the lobby renders `LobbyConnecting`: the real two-card layout filled with pulsing skeleton bars (code, seats, player rows, actions) and `aria-busy="true"`, so a slow connection reads as "still connecting" instead of a broken screen. `describeLobby` says **Creando la partida…** / **Conectando con la partida…** / **Conectando…** in those phases.
- **Lobby:** left card shows the live status from `describeLobby`, the room code (`RoomCode`) and the guest count. Right card lists every seat (`LobbySeat`): avatar, name, **Anfitrión**/**Invitado N** and the seat's board colour; empty seats read **Asiento libre · lo ocupa un bot al empezar**. The list updates in real time from the host's `LOBBY` message or the guest's own session snapshot.
- **Start authority:** only the host sees **Iniciar la partida**, always enabled — the host starts whenever they decide, and empty seats are filled by bots. Guests see a Spanish note saying only the host can start, plus **Salir**. The host sees **Cancelar**.
- **Game:** once the session carries a state and roster, the flow renders `PartyGameScreen` (shared `GameStage`, host-authoritative party session) with no intermediate step. Leaving returns home and tears the session down.
- **Support:** `getLanSupport()` is checked once; when the browser lacks a secure context or `RTCPeerConnection`, the create step disables the online option and explains why.
- **Accessibility/copy:** every visible string is Spanish with accents; every drawably button and clickable tile carries `select-none`, while the name and code inputs stay selectable.

## Playable game (`/play`, implemented)

- **Route and mode:** `app/play/page.tsx` reads the create step's query settings after a Suspense boundary (`useSearchParams`). It supports **all-vs-all** (human + three bots) and **1 vs 1** (human + the opposite-corner bot). The human sits bottom-left in the rotated view and can choose any colour; the chosen colour determines the view rotation, starting square and pointer-selectable chips. The engine turn order is the fixed **blue → red → yellow → green** filtered to the participants. React owns the `GameState`; every action uses the pure engine (`roll`, `chooseBarrier`, `applyMove`, `applyBonusMove`). There is no network, persistence, or authentication layer; the whole route is precached and playable offline, reloading starts a new game, and auto-mode is in-memory only.
- **Human vs bots:** only the human's chips are pointer-selectable; the board receives `humanPlayerId` plus `humanControlled` and clears `selectableTokenIds` during bot turns and while auto-play is on. Keyboard move targets and move popovers are rendered only while the human controls their turn. The human's dice tray is the only visible roll button; bot trays are textless and automatic. Human controls are unavailable while a bot acts; the header restart/back controls remain available. In 1 vs 1 only two seat cards are rendered at opposite view corners; the other two board homes stay empty.
- **Empty seats (local four-player table):** the create step's **Huecos de la mesa** list appears when **No, contra bots** is selected. It shows the human's own colour as a fixed **Tu asiento** row and, for each other colour, a drawably trigger that opens a HeroUI popover (`components/setup/seat-fill-picker.tsx`) with **Jugar con un bot** / **Dejarlo vacío**. Empty colours are stored as `GameSettings.emptyColors` and travel to `/play` as the comma-separated `empty` query parameter. `createGameSetup` filters those colours out of the roster, so the engine seats 2–4 players; `getGameSettingsFromSearchParams` never empties the human's colour, ignores `empty` for `1v1`, and clamps to at most two empty seats so a rival always exists. The picker disables **Dejarlo vacío** when the table is already at two seats.
- **Empty seats (online room):** the host decides per unoccupied guest seat, in the lobby itself. Each empty seat row renders the same `SeatFillPicker` (compact variant, labelled **Invitado N**), and `party.setSeatEmpty(seatId, empty)` forwards to `WebRTCHostSession.setSeatEmpty`. The host session keeps `emptySeats`, rejects the host's own seat, seats already held by a connected guest, and any change that would leave fewer than two seats, then broadcasts an updated `LOBBY`. A guest who connects into a seat that was marked empty automatically takes it over (`refreshLobby` drops it from `emptySeats`). `buildRoster(mode, humans, emptySeats)` skips the empty seats, so the match starts with 2–4 players; `buildConfigs(roster, mode)` keeps the room's colour map, so a two-seat `all` room still uses the four-seat colours. The lobby copy adds “N asientos quedarán vacíos” and the seat row reads **Sin jugador · queda vacío en la partida**.
- **Auto-play:** a drawably checkbox labelled **Modo automático** sits above the human dice tray in the human seat (never in the header). Checking it hands the human's seat to `lib/bots/policy.ts`: the same 1 s wait, 1 s dice tumble and 1 s move pacing, with the human's dice/barrier/bonus/board controls hidden (`DiceCard.controllable=false`, `humanControlled=false`, empty keyboard/popover targets). The human panel reads **Tú (auto)** and the active tray shows an **Auto** badge. Unchecking clears the pending scheduler timer and any in-flight auto roll, then restores the human controls immediately; the bot action re-checks an `autoModeRef` so a timer racing the toggle cannot act. Auto mode persists across “Nueva partida” but not navigation/reload.
- **Bot policy:** `lib/bots/policy.ts` is pure, deterministic and one-ply. It consumes only the public `GameState` and the legal move lists. It scores captures (+1000), exact goals (+800), forming a friendly barrier (+300), safe landings (+150), progress (+1 per target square), risky non-safe landings within 1–6 of an opponent (−200) and breaking an own barrier (−150 unless capturing or reaching the goal). Ties favour higher target progress then token id lexicographically. It also chooses the highest-value legal bonus and, when several own barriers are breakable, simulates each engine break and keeps the best resulting position. It never returns an illegal move. The same policy drives the auto-play human seat.
- **Bot pacing:** when a bot (or the auto-play human) becomes current, the controller waits **1 s**, rolls with a **1 s** dice tumble, waits **1 s**, then applies the chosen move/bonus/barrier break (also 1 s after each state change). Every state change clears the pending timer; the bot action checks the phase and player again before applying. Bot/auto timers and the human roll timers are cleared on reset/unmount.
- **Current rules (two-dice variant):** two d6 are always thrown and never summed; each die is a separate move and both must be used while both have legal moves. A 5 die releases one token automatically and is spent; a total of 5 spends both dice and releases one token; double 5 releases two tokens when the start allows. Doubles grant an extra roll; the third consecutive double sends the last moved outer-track token to the yard. ### Offline shell (implemented; Task 05)

- **Integration choice:** the service worker is hand-written and generated, not Serwist. `@serwist/turbopack` 9.5.13 is the current stable Turbopack integration, but its route-handler implementation explicitly targets projects **without** `cacheComponents`, which this app enables (`next.config.ts`), and the Serwist 10 line is still a preview. The brief permits a hand-written worker plus a generated precache manifest as a fallback; the fallback was chosen to avoid a build-time incompatibility. `@serwist/next`'s webpack plugin cannot be used with the Turbopack build.
- **Source and output:** `scripts/service-worker-template.js` is the source; `scripts/generate-service-worker.mjs` replaces `__BUILD_REVISION__` and `__PRECACHE_MANIFEST__` and writes `public/sw.js` after `next build`. `public/sw.js`, `public/sw.js.map` and `public/swe-worker*` are generated and git-ignored. The worker is served at `/sw.js`.
- **Build-adapter compatibility:** the generator reads `.next/prerender-manifest.json` to confirm the four offline routes are prerendered, instead of requiring `.next/server/app/*.html` to exist on disk. Build adapters that run `onBuildComplete` (for example Vercel's, which packages and relocates those HTML files into `.vercel/output` before `next build` exits) would otherwise make the post-build step fail with `Missing prerendered route`. The worker precaches URLs, not files, so the HTML files are only measured for the logged size and are skipped when absent.
- **Precache:** all app routes needed offline (`/`, `/play`, `/offline`), `/manifest.webmanifest`, `/favicon.ico`, every `/_next/static/**` file (JS chunks, CSS, hashed `next/font` media), and every file under `public/` (icons, avatars, chip/token art, dice faces/source art, mode images, supplied sounds, result artwork, button icons, font originals and starter SVGs). The generated worker itself is excluded. The current build produces 98 entries, about 60.7 MiB. The build ID from `.next/BUILD_ID` is the cache revision and is embedded in the worker.
- **Navigation:** network-first with a 3 s timeout and `navigationPreload` where supported. On a network failure/timeout, the matching precached route is used (`/`, `/play`, `/offline`, query strings ignored); any other path falls back to `/offline`. A network 4xx is returned as-is; a 5xx falls back to cache.
- **Static assets:** cache-first from the versioned precache, with a runtime cache for uncached same-origin static files. Audio range requests are answered with a `206 Partial Content` slice from the cached body. `next/image` optimizer responses are cached after first use; when offline (or when the optimizer fails), the worker serves the original precached public image for the `url` query parameter, so changing avatars and rolling dice still work on a cold offline load.
- **API and WebSocket boundary:** `/api/*` is never intercepted or cached. WebSocket traffic is not intercepted, cached or replayed. No background sync, offline mutation queue, push notification or party-data caching. Online parties require connectivity.
- **Client-router payloads:** requests with `RSC`/`Next-Router-Prefetch` headers are left network-only. Offline, Next.js falls back to a document navigation, which the worker serves from the route cache (verified with the `/play` → `/` "Volver al inicio" button).
- **Cache lifecycle:** cache name `parchis-stars-<buildId>`; `skipWaiting: true` and `clients.claim: true`. Activation deletes every `parchis-stars-*` cache with a different build ID. The page is not automatically reloaded on `controllerchange`; a new build activates and the next load uses it.
- **Registration:** `app/service-worker-register.tsx` is mounted once in `app/layout.tsx`. It registers `/sw.js` with scope `/` and `updateViaCache: "none"` only in production, only in a secure context and only when `serviceWorker` exists. In development it unregisters any leftover worker instead of registering one, so HMR is never controlled by a stale production cache. Errors are logged; rendering is never blocked.
- **Headers (`next.config.ts`):** `/sw.js` gets `Content-Type: application/javascript; charset=utf-8`, `Cache-Control: no-cache, no-store, must-revalidate` and `Service-Worker-Allowed: /`; `/manifest.webmanifest` gets `Cache-Control: no-store`.
- **Offline page:** `app/offline/page.tsx` is a static, precached drawably card with the Spanish heading **Sin conexión**, the body **No hay conexión a internet.**, a **Reintentar** reload button, and a native form button back to **Jugar sin conexión** (`/`). Online play is not offered there because pairing needs connectivity. It uses the same paper/ink theme and needs no network.
- **Offline indicator:** `app/offline-indicator.tsx` listens to `online`/`offline`, reads `navigator.onLine` as a hint only, and renders a fixed, `pointer-events-none` drawably badge with **Sin conexión** while offline. It causes no layout shift and does not disable actions.
- **Build/start:** `bun run build` runs `next build && node scripts/generate-service-worker.mjs`; `bun run build:sw` regenerates the worker from the current `.next` build; `next start` serves the result. There is no Task 04 custom server (`server.ts`) in this repository, so production testing used `next build && next start`; the existing `next dev` server is unaffected and registers no worker.
- **Offline gameplay (extends the Task 05 brief):** all local → `/play` assets are precached, so 1v1 and all-vs-all bot games load and play on a cold offline reload, including PixiJS board textures, avatar/mode/dice images, sounds and range requests. Online parties remain network-only.

## Desktop (Tauri v2)

- **Why a static export:** Tauri has no Node.js server. `scripts/build-desktop.mjs` runs `next build` with `TAURI_BUILD=1`, and `next.config.ts` then sets `output: "export"`, `images: { unoptimized: true }` and `trailingSlash: true`; the result is written to `out/`. The normal `bun run build` is untouched and still enables `cacheComponents`, `partialPrefetching` and the PWA headers.
- **Embedded assets:** `tauri/src-tauri/tauri.conf.json` sets `build.frontendDist` to `../../out`. `tauri::generate_context!()` (tauri-codegen) embeds every file in that directory (HTML, RSC payloads, `_next/static` chunks, fonts, images, sounds, manifest) into the Rust binary at compile time. The webview loads them from the Tauri custom protocol, so the desktop app is fully offline with no cache layer and no runtime downloads.
- **Manifest:** `public/manifest.webmanifest` is a static file so it survives the static export without a route handler; `app/layout.tsx` links it with `manifest: "/manifest.webmanifest"`.
- **Service worker:** `app/service-worker-register.tsx` uses the shared `isTauriRuntime()` helper (`__TAURI_INTERNALS__`, `window.isTauri`, `tauri:` protocol or `tauri.localhost`) and unregisters any leftover worker instead of registering one. `scripts/build-desktop.mjs` also removes `sw.js`/`swe-worker*` from `out/` so the desktop bundle does not ship a dead worker.
- **Audio:** `components/game/game-feedback.ts` keeps the direct `/sounds/*.mp3` path on the web, macOS and Windows. On Tauri + Linux it fetches each clip and plays a blob URL because WebKitGTK/GStreamer has no URI handler for `tauri://` media; without this the supplied dice and movement clips are silent in Linux release builds.
- **Project layout:** `tauri/src-tauri/` contains `Cargo.toml`, `build.rs`, `src/main.rs`, `src/lib.rs`, `tauri.conf.json`, `capabilities/default.json` and generated desktop icons. `scripts/tauri.mjs` runs the CLI from that directory while the CLI itself stays a root dev dependency (`@tauri-apps/cli`), keeping one `bun.lock`.

## Game engine (implemented; Classic two-dice variant)

- **Location:** `lib/parchis/`, imported as `@/lib/parchis`. Pure TypeScript with zero imports from React, PixiJS, Next.js, the DOM, or the network. No runtime dependencies.
- **Modules:**
  - `constants.ts` — board geometry and rule numbers (the contract the PixiJS board must render): track/home/goal, safe squares, capture/home bonuses, `DOUBLES_PENALTY_COUNT`.
  - `types.ts` — public JSON-safe types: `GameState` with `schemaVersion: 2`, `dice: [DieState, DieState] | null`, `consecutiveDoubles`, `barrierChoice`, `Move` with a `die`, `BonusMove`, `GameEvent`, etc.
  - `errors.ts` — `GameError` with stable `code`s: `INVALID_PLAYERS`, `INVALID_ROLL`, `INVALID_POSITION`, `WRONG_PHASE`, `ILLEGAL_MOVE`, `MUST_MOVE`, `INVALID_BONUS`, `INVALID_BARRIER`, `GAME_OVER`, `INVALID_STATE`.
  - `rules.ts` — pure helpers: track mapping, occupancy, barriers, entry check, `checkAdvance`, `getRemainingDice`, per-die `getLegalMoves`, `getOwnBarriers`, `getEligibleOwnBarriers`, `getBarrierBreakMoves`, `pickAutoBarrierBreak`, `getLegalBonusMoves`, `validateState`.
  - `engine.ts` — actions: `createGame`, `rollDie`, `rollDice`, `roll`, `chooseBarrier`, `applyMove`, `applyBonusMove`, `isFinished`, `getWinnerId`. No manual pass.
  - `presentation.ts` — pure engine→artwork bridge used by the UI: colour mapping (engine red→board green, blue→blue, yellow→red, green→yellow), `getTokenViews` (yard/track/corridor/goal placement and stacking), destination views, two-die views with used flags, board-percentage anchors that rotate with a player view, and Spanish progress labels with optional view-relative numbering.
  - `index.ts` — the only public entry point.
  - `test-helpers.ts`, `*.test.ts` — test-only (position builder, deep-freeze, seeded `mulberry32`); not re-exported.
- **Ruleset (Classic two-dice variant):** two d6, **always separate, never summed**. Each die is one movement; both dice must be used while each has a legal move. A 6 moves 6 (no 6→7). Entry is automatic and mandatory: a 5 die releases one token and is spent; a total of 5 (1+4, 2+3) releases one token and spends both dice; double 5 releases two tokens when the start allows. Doubles grant another roll. The third consecutive double is not used for movement and sends the last moved outer-track token back to the yard (home column/goal exempt). Both dice even trigger the own-barrier rule. Base Classic rules are preserved: capture +20 bonus, goal +10 bonus, exact goal, safe squares, barriers, private home column/goal. No 6 extra roll and no three-sixes penalty; no legal move auto-passes.
- **Own barriers with two even dice:** one die must break an own barrier by moving one of its two tokens. If exactly one own barrier is breakable, the engine picks the first legal break (token order, then die order) and executes it automatically. If two or more are breakable, the state enters `awaiting-barrier` and the player chooses the barrier; the engine then executes the same deterministic break. If an own barrier exists but neither die can break one, the turn is skipped automatically without spending the dice.
- **Classic vs Spanish mode:** classic forbids two different colours resting on the same safety square (landing there is illegal, passing is allowed); Spanish mode is out of scope. Mixed-colour blockades cannot exist.
- **Board constants:** 68 outer squares; starts at 0/17/34/51 (red/blue/yellow/green); route progress 0–63 on the outer track (absolute index `(start + progress) % 68`), 64–70 in the private home column, 71 at the goal; 12 safe squares `0, 7, 12, 17, 24, 29, 34, 41, 46, 51, 58, 63`. Each colour's home entrance (progress 63) is safe because it is another colour's start+12.
- **Visual counterpart:** `lib/parchis/board-geometry.ts` owns the 21×21 reference layout, chamfered inner corners, corridors, yard slots, and physical/view-aware positions. The artwork's starts (5/22/39/56) and the engine's starts (0/17/34/51) differ by a constant +4, so `presentation.ts` maps engine red→board green, blue→blue, yellow→red, green→yellow and reuses the token's engine progress unchanged. The board paints the starts in their corridor colour and the eight brown/dark safe marks at start +7/+12: 12/17, 29/34, 46/51, 63/68. Four of those are also entrance tips (17/34/51/68) and are safe. `getViewCorner` rotates the four home corners for the human's perspective.
- **Occupancy:** max 2 tokens per outer square, same colour only. Two tokens form a barrier that blocks passing and landing for everyone (owner included), except the both-even own-barrier break above. Home column and goal are private, unlimited and capture-free.
- **State:** JSON-safe and fully public (`schemaVersion: 2`, `mode: "classic"`), no `Map`/`Set`/`Date`/functions. The two die values are supplied by the caller (`rollDice(random)` is a helper); each `DieState` carries a `used` flag. Actions are taken implicitly by the current player; the caller authenticates the sender.
- **Purity:** every action validates first, then returns a new state built from copies; inputs (even deep-frozen) are never touched. On error the state is unchanged.
- **Phases:** `awaiting-roll` → `roll` (automatic entries and barrier resolution) → `awaiting-barrier` when the player must choose one of several breakable own barriers → `awaiting-move` (one die per move, in any order, on one or two tokens) → optional `awaiting-bonus` (`applyBonusMove`, mandatory; auto-forfeited and logged when no legal bonus; the bonus spends no die) → automatic pass if no remaining die has a legal move → extra roll on a double (same seat, same `turn`) or next seat (`turn + 1`, rolls/doubles/last-moved/bonus/barrier reset) → `finished` when one player has all four tokens at the goal.
- **Doubles:** a double grants another roll after all dice/bonuses resolve; the third consecutive double is handled inside `roll` and never reaches a move phase. A no-move double still grants its extra roll. A no-legal-barrier-break skip does not grant the extra roll.
- **Event log:** append-only `log` of `roll` (dice pair), `enter` (die or null for sum 5), `advance` (die), `barrier-break` (die, square, automatic), `capture`, `bonus-move`, `bonus-forfeited`, `pass`, `three-doubles`, `win`; every event carries its `turn`. UI layers narrate/animate from it.
- **Tests:** `bun test` (106 tests / 4,752 assertions across engine, rules, simulation, geometry, presentation, bot policy, local setup, feedback cues and result copy: setup, automatic entries (5/sum 5/double 5), separate dice/order/splitting, auto-pass, both-even own barriers (auto, choice, blocked skip), doubles/three-doubles, base Classic captures/safe/barriers/bonuses/win, purity/JSON, view corners and view-relative labels, bot capture/barrier/goal/risk/barrier-break/bonus/barrier-choice scenarios, feedback cue priority, win/loss result copy and artwork, plus 500 seeded two-dice games with invariant checks and a determinism replay). The simulation ran 176,423 actions (longest 639). The original Task 03 audit found no deviations in the one-die base rules; the two-dice variant is specified by the project owner and covered by this suite.
- **Boundary:** the engine owns rules only. PixiJS renders the board; React/drawably render app chrome; networking (Task 04) and the local controller (Task 06) call these functions.

## Online party (WebRTC gameplay, HTTP signaling) — implemented

> Replaces both the earlier serverless LAN mode and the single-opponent `/versus` screen. Gameplay is still peer-to-peer over WebRTC with a host-authoritative session; the HTTP signaling server now seats a room of **2 or 4** players and only swaps a **six-character room code**. There is no WebSocket, no custom Node server and no TURN.

- **Topology:** a star. The host holds one `RTCPeerConnection` and one ordered, reliable `RTCDataChannel` (`parchis-v1`) per guest, so a four-player room has three direct connections and guests never talk to each other. The HTTP server relays WebRTC descriptions and presence only.
- **Seats:** the host is board **red**, guests take **yellow**, **blue** and **green** in join order (`SEAT_BOARD_COLOR` in `lib/party/protocol.ts`, `buildRoster`/`buildConfigs` in `lib/party/seats.ts`). A `1v1` room instead seats the guest on the **opposite corner in green**, matching the local 1v1, so the two seats are diagonal rather than adjacent. IDs are `host`, `guest-1`…`guest-3` and `bot-{red,yellow,blue,green}`. Engine turn order stays blue → red → yellow → green. A `1v1` room seats two (host red, guest yellow); an `all` room seats four.
- **Bots fill empty seats:** the host starts whenever it wants. `buildRoster(mode, humans, emptySeats)` fills every unoccupied seat with the bot for that colour **unless the host marked it empty**, and `WebRTCHostSession` plays bot seats (and any guest that dropped mid-match) with `lib/bots/policy`. A room always keeps at least two seats.
- **Seat hygiene (feedback fixes):** every join increments a seat `epoch`, and signals carry the sender/recipient epoch. A reused seat never receives the previous occupant's SDP, a `left` note survives only until the seat is reused, and the store purges signals on leave/join and prunes read/expired ones, so a long lobby cannot fill `MAX_SIGNALS_PER_ROOM`. `POST { action: "start" }` marks the room started; a later `join` fails immediately with `ROOM_STARTED` instead of waiting 20 s for a data channel. A signal addressed to a seat that just left returns `PEER_GONE` (409) and the host drops that seat instead of ending the whole lobby.
- **Signaling server (`app/api/versus/route.ts` → `lib/server/versus/rooms.ts`):** `POST` handles `create` (optional `capacity` 2/4 → code + 64-hex host token), `join` (first free guest seat), `signal` (an offer/answer/bye string plus an optional `to` seat) and `leave`; `GET ?code=&id=&since=` returns that peer's new signals, presence (`{ host, guests[] }`), capacity and a `closed` flag. Tokens travel in the `Authorization: Bearer` header or the POST body, never in a URL. `join` pushes a `joined` note to the host, `leave` a `left` note; the host turns those into connection attempts or teardowns. Payloads cap at 20,000 chars, rooms at 64 signals; rooms expire after 30 min of activity, or 10 min after creation while guest-less. A host leaving closes the room; a guest leaving frees its seat for the next join. The store is Redis-backed (`lib/server/versus/redis-store.ts`): each room is one JSON value keyed by code and mutations run under a short per-room lock, so any serverless instance can serve the next poll. A Redis failure returns `STORE_UNAVAILABLE` (503), which the client reports as `server-unreachable`. The in-memory store remains for tests. Nothing is logged.
- **Pairing flow:** the host polls for `joined` and, for each new seat, creates the channel **before** the offer, gathers ICE non-trickle, posts the offer addressed to that seat and keeps polling. The guest types the code (retried up to 3× while the room propagates), polls, decodes the offer, answers, and waits for its data channel. `CONNECT_TIMEOUT_MS` (20 s) surfaces a Spanish failure. Descriptions are structurally validated by `lib/party/versus/description.ts` before reaching `RTCPeerConnection`.
- **HTTP client (`lib/party/versus/signaling-client.ts`):** `capacityForMode`, `createVersusRoom(capacity)`, `joinVersusRoom` and `VersusSignalingClient` (`send(kind, payload, to)`, `poll`, `leave`, 700 ms interval). Failures map to `room-not-found`, `room-full`, `room-closed`, `unauthorized`, `bad-request`, `server-error` or `network`; malformed responses are rejected rather than trusted.
- **Lobby state (`lib/party/versus/lobby.ts`):** a pure, tested reducer `choosing | creating | host-lobby | guest-form | joining | guest-lobby | connected | failed` carrying role, mode, code, capacity, `emptySeats`, failures and the live player list, plus Spanish `describeLobby`/`seatLabel` copy. `usePartySession` (`lib/party/versus/use-party-session.ts`) wires it to the signaling client, one peer connection per guest on the host and one on each guest, and exposes `createGame(mode)`, `openJoin()`, `joinGame(code)`, `startGame()` and `setSeatEmpty(seatId, empty)` (both host only), `retry()` and `abort()`.
- **ICE and TURN:** the browser fetches `GET /api/ice`, which mints **short-lived Cloudflare Realtime TURN credentials** server-side (`lib/server/versus/turn.ts`) and caches them for 30 minutes. The Cloudflare API token never reaches the client. When TURN is not configured or Cloudflare fails, the route returns a STUN-only list, so online play still works without relay. Non-trickle gathering resolves on `icegatheringstate === "complete"` or an end-of-candidates null candidate, with a 2.5 s cap. `RTCPeerConnection` only exists in a secure context and the flow screens that.
- **Connection mode:** after the data channel opens, `lib/party/webrtc/connection.ts` reads the nominated `candidate-pair` from `getStats()` and exposes each seat's candidate type (`host`, `srflx`/`prflx`, `relay`). The host broadcasts it in a `CONNECTION` message; the lobby seat and the in-game player panel show "Conexión directa · host/STUN" or "Conexión por TURN · relay" under each player. This makes a TURN fallback visible instead of silent.
- **Authority:** unchanged. The host owns `GameState`, the version counter and the dice. `lib/party/authority.ts` validates actor → current turn → version → phase, applies the action through the pure engine, increments the version and extracts new events. Only `ROLL` draws dice, with `crypto.getRandomValues`; guest actions are rate-limited and every peer is checked against the roster.
- **Protocol v4:** `HELLO { protocol, player }` and `ACTION` (guest → host), `LOBBY { mode, players, emptySeats }`, `START { version, mode, roster, state }`, `STATE`, `ERROR`, `CONNECTION { connections }` and `BYE` (host → guest). `CONNECTION` carries `{ transport, candidate }` per human seat and is validated like every other message. The roster is a `{ players }` list of 2–4 players with stable ids; `emptySeats` lists unoccupied guest seats the host left without a bot, and `START.mode` keeps the room's colours even when it seats only two. All messages are structurally validated by `decodeWireMessage`; inbound is capped at 64 KB. SDP and state are never logged or persisted.
- **Sessions:** `lib/party/sessions/webrtc-host-session.ts` takes `{ host, mode }`, `joinPeer({ playerId, transport })` once per guest, `removePeer`, and `start()`, which builds the roster + game, broadcasts `START` and schedules bot steps. `webrtc-guest-session.ts` takes `{ transport, playerId, player }`, sends `HELLO` on open and adopts `LOBBY`/`START`/`STATE`. Both expose the shared `GameSession` surface, so `GameStage` stays transport-agnostic.
- **UI:** `PartyGameScreen` reuses `GameStage` with `remoteHuman` and never passes `autoControl`, so the online seats never offer or display **Modo automático**; it labels the opponent **Rival**, echoes the committed dice from the newest `roll` event, and shows a slow-connection banner after 4 s without a `STATE`. There is no rematch and no host migration.
- **Trust:** guests trust the host's state and dice (no anti-cheat, no ranked play). This is a friends-only mode.
- **Offline and desktop:** the homepage is precached, but online play needs connectivity and the static Tauri export has no signaling server, so `TAURI_BUILD=1` drops `route.ts` files by setting `pageExtensions` to `["tsx", "jsx", "js"]`. The desktop app can still play local bot games.
- **Deployment:** rooms live in Redis with the same TTLs (30 min active / 10 min empty) and a 5 s per-room mutation lock, so Vercel instances share state. The route is dynamic and relies on the default Node.js runtime. A Redis outage returns `STORE_UNAVAILABLE` (503). Bots planned by the host run on the host only.

## Realtime parties and networking (planned Task 04)

- **HTTP:** Next.js App Router route handlers under `app/api/parties/` create parties, join by code, expose public lobby info, and return authenticated reconnect snapshots.
- **WebSocket:** Next route handlers cannot perform an HTTP upgrade, and serverless hosts drop long-lived sockets. A custom Node server (`server.ts`) runs Next plus a `ws` server and handles `/api/ws`; all other upgrades (including dev HMR) are forwarded to `app.getUpgradeHandler()`.
- **Scripts:** `bun dev` / `bun start` run `tsx server.ts`, not `next dev` / `next start`.
- **Store:** a single in-memory `PartyStore` attached to `globalThis` so the custom server and Next route-handler bundles share it. The store is the only room source of truth and emits events that the WS layer broadcasts.
- **Rooms:** 6-character codes, up to 4 players, 2–4 to start, host is seat 0, colour assignment at start (2 → red/yellow, 3 → red/blue/yellow, 4 → all), versioned state.
- **Auth:** raw 32-byte player tokens are returned once; only SHA-256 hashes are stored. Tokens are sent in the AUTH message, never in URLs.
- **Protocol:** JSON messages over `/api/ws`, protocol version 1. Clients AUTH first, then send `START`, `ROLL`, `MOVE`, `BONUS_MOVE` with the last seen version. The server rolls the die, validates through the pure engine, increments the version, and broadcasts the authoritative state plus new events.
- **Reconnect:** a valid player token restores the full snapshot; one active socket per player (`4001 REPLACED` on replacement).
- **Transport abstraction (Task 04):** `lib/party/transport.ts` defines `GameTransport`; the abstract `GameSession` is the only game API the UI may use. `WebSocketGameSession` is the first implementation; Task 07 adds WebRTC host/guest sessions without changing callers. `lib/party/authority.ts` holds shared, browser-safe action validation/auto-pass used by the server and the future P2P host.
- **Deployment:** requires a long-lived Node process (or a managed WS service). Vercel/serverless functions are unsupported for this layer. Rooms are lost on restart and the store is single-instance; horizontal scaling needs an external store/pub-sub.
- **Boundary:** `lib/party/` is shared protocol/client; `lib/server/party/` is server-only. Route handlers must not import `ws` or browser code.
- **Seats are the source of truth for colours:** any new screen must derive board/engine colours from `lib/party/seats.ts` rather than hard-coding host/guest colours.

## Local bot mode (direct `/play` implementation; full Task 06 pending)

## P2P 1v1 (planned Task 07 — gated; an HTTP-signaled online 1v1 is implemented above)

> **Gate:** Task 07 must only be started after Tasks 01–06 are complete and their `results/` summaries exist.
>
> **Note:** the online party documented above covers the WebRTC goal with a plain-HTTP signaling relay and room codes. What remains below is the WS-signaled `/versus/[code]` version; it is not implemented.

- **Topology:** two players in a `p2p-1v1` room. The existing WebSocket server handles only signaling/presence; all gameplay messages travel over a reliable, ordered WebRTC `RTCDataChannel`.
- **Authority:** the host peer owns the engine state, version, dice, and validation; the guest sends actions and adopts snapshots. This mirrors Task 04 and reuses the shared, browser-safe `lib/party/authority.ts`. The guest trusts the host; no anti-cheat or ranked play.
- **Session API:** the UI/`GameStage` depends only on the abstract `GameSession` from Task 04. `WebSocketGameSession`, `WebRTCPeerHostSession`, and `WebRTCPeerGuestSession` expose identical calls (`start`, `roll`, `move`, `bonusMove`, subscribe/dispose); `createGameSession(...)` selects the implementation from the room mode/role.
- **Signaling:** authenticated WS messages relay SDP offers/answers and ICE candidates only to the other player. Signaling payloads are size-capped, never persisted or logged; P2P rooms reject game actions over WS with `WRONG_TRANSPORT`.
- **ICE/TURN:** `GET /api/p2p/ice-servers` returns authenticated STUN/TURN config. TURN is needed for some NATs; credentials must be ephemeral and never committed.
- **Rules/UI:** host = red, guest = yellow, 2-player engine rules. Route `/versus/[code]`; the lobby uses drawably chrome and the game reuses Task 06's Pixi `GameStage`.
- **Lifecycle:** signalling reconnects independently; a dropped data channel pauses play and the host attempts an ICE restart and resends a full state snapshot. No host migration; a host reload ends the match. No silent fallback to WebSocket gameplay.
- **Out of scope:** 3–4 player P2P mesh, host migration, ranked/anti-cheat, matchmaking, rematches, and offline P2P (WebRTC needs network).

## Data and networking

- Game rules live in the pure engine (`lib/parchis/`); it has no UI, network, or persistence dependencies.
- Signaling rooms and relayed SDP live in Redis with TTLs, shared by every serverless instance. Game state stays in host memory and is never persisted. No accounts, database of results, or server-authoritative game state yet.
- The full game state is public (no hidden information) and JSON-safe, so the server can broadcast it to every player.

## Conventions

- Read the relevant guide in `node_modules/next/dist/docs/` before writing code (per `AGENTS.md`).
- Prefer `drawably/react` for every control and container.
- Use PixiJS for the game board, tokens, board animations, and all board/game-state updates. Use drawably/react for the UI around the game; the current `/play` dice cards are a direct owner-requested exception. Keep the two layers separate.
- Every button or button-like control uses `select-none` (Tailwind) to prevent text selection on mobile long-press/double-tap. Native inputs and textareas stay selectable.
- All user-facing copy is in **Spanish**, even when briefs and code are in English: headings, buttons, labels, placeholders, helper/error text, metadata, manifest strings, and accessibility labels. Code identifiers, comments, and technical docs stay in English.
- Keep interactive pages as small client components; keep the root layout a server component.
- Keep server-only code in `lib/server/`; never import it from client components. Shared protocol/types live in `lib/party/protocol.ts` and must stay dependency-free.
- The server is authoritative: dice rolls, turn order, legal moves, and party membership are validated server-side. Clients never send die values or game state mutations that bypass the engine.
- Never log or put player tokens in URLs; store only token hashes server-side.
- Local/bot mode (`/play`) must make no network calls and must not import `lib/party` client code or `lib/server/*`; the setup flow at `/` is the only place that talks to the signaling server. The engine + local controller are the only sources of truth there.
- The service worker is production-only and must never cache `/api/*`, WebSocket traffic, tokens, or party data.
- UI/game components depend only on the `GameSession` surface, never on a concrete transport. WebSocket and WebRTC sessions must expose the same calls; do not add transport checks to `GameStage` or screens.
- Accessibility is part of the UI: real labels, keyboard support, visible focus, `aria-pressed` / `aria-selected` where relevant.
- Respect `prefers-reduced-motion`; drawably already freezes boil and hover re-sketches. Do not add extra motion.
- Never edit `AGENTS.md` as part of a task.
- Each task file starts with the instruction to read `AGENTS.md` before changes and to update this document after.
